# D4.4 — Source of truth

**Status:** 🟡 draft, awaiting review
**Date:** 2026-10-24
**Scope:** for every fact the system relies on, exactly one authority — and for every copy, a way to
rebuild or verify it.

## The rule

> **One fact, one owner. A copy is never authoritative; it is a cache with a check.**

Two copies of the same fact will disagree eventually. The design question is not "how do we prevent
that" but "when they disagree, which one wins, and how would we know".

---

## 1. The facts, and who owns them

| Fact | **Authoritative owner** | Copies that exist | Rebuild or check |
|---|---|---|---|
| The email itself | **Gmail** (the user's mailbox) | `inbound.raw_body`, `inbound.snippet` | Re-fetch from Gmail. Beyond our 7-day window and the user's own deletion, the copy is the only one left |
| What we extracted from it | `inbound.parsed` | `applications` row, if confident | `reprocess()` re-runs the rules over the raw body |
| The application's company and role | `applications` | — | Only a user edit changes them |
| The application's **current** stage | `applications.stage` | `events` (as history, never as state) | Corrections write an event; the column is the answer |
| The application's **history** | `events` | — | Append-only; cannot be rebuilt, must never be lost |
| When the application last changed | `applications.last_activity_at` | — | Recompute `max(events.occurred_at)`; nightly check compares |
| What exists as a due item | `due_items` rows generated by `planning` | — | `sync()` regenerates from applications + rules |
| What the user decided about an item | `due_items.state`, `snoozed_until` | — | **Authoritative. Never regenerated** |
| Whether this week's digest went out | `digests` row | — | The unique key is the answer |
| Who the user is | `auth.users` (Supabase) | `profiles.id` | FK, cascade |
| The user's timezone | `profiles.timezone` | — | — |
| Counts and analytics | **nothing** | — | Computed on demand from `events` and `applications` |

---

## 2. The three external authorities

Some facts are not ours to own, and pretending otherwise causes bugs:

1. **Gmail owns the emails.** Our database is a *projection with a retention window*, not the archive.
   This is why the 7-day purge is safe: the original still exists. It is also why losing the database
   is survivable (R4) — and why losing the Gmail account is not (R2).
2. **Supabase Auth owns identity.** `profiles` is a satellite table, not a second user table.
3. **The user owns their decisions.** Done, snoozed, dismissed, corrected — no rule may overwrite
   them. A parser improvement may change what we *propose*; it may never change what *you decided*.

That third one is the rule that makes `reprocess()` and `sync()` safe to run at any time.

---

## 3. The copies we accept, and the checks

| Copy | Why it exists | Drift check |
|---|---|---|
| `applications.last_activity_at` | The silence rule needs "quiet for 10 days" without scanning events on every page load | Nightly: recompute from `events`, report any row where they differ by more than a minute |
| `inbound.parsed` | Lets Review show what the parser thought, and lets a re-parse diff against it | `reprocess()` recomputes; a diff is informational, never automatic |
| `events` (as history of `stage`) | Timeline and future analytics | A `stage_changed` event must match the stage written in the same transaction (invariant 17) |
| `due_items` generated rows | Fast due list | `sync()` is idempotent via `(owner_id, key)`; regenerating must produce the same set |

**The nightly reconciliation job is the price of having copies at all.** It is small: three queries
and a log line. Without it, a denormalised column is a rumour.

---

## 4. What we deliberately do not store

| Not stored | Why | Where it comes from instead |
|---|---|---|
| Counts of applications per stage | A stored count is a second truth that drifts | `count(*)` on demand |
| "Days since last activity" | Derived from a timestamp | Computed at render |
| Whether an application is "stale" | A rule, not a fact | `planning` decides at read time |
| The digest's contents | It is generated per send | Rebuilt from `due_items` |
| Any user-visible derived value | Same reason | Computed |

At this scale (tens of rows) computing on demand is free. Storing derived values is a technique for
when reads are expensive — not a default.

---

## 5. Two decisions recorded here

### Decision 1 — Is `last_activity_at` a column or a computation?

| Option | Strength | Weakness |
|---|---|---|
| **A. A column, written in the same transaction as the event** (chosen) | The silence query uses one index; no per-row subquery | A copy that can drift if a write path ever skips it |
| B. Always computed from `events` | Cannot drift; one less write | Every due-list query becomes a join with a `max()` per application |

**Recommendation: A**, with the nightly reconciliation from §3 as the mitigation. The invariant table
already forces the write into the same transaction (rule 17), so drift requires a bug *and* a missed
nightly check.

### Decision 2 — Is the current state or the event log authoritative?

**The current state.** `applications.stage` is the answer; `events` is the history. Full event
sourcing was rejected in ADR 0007, and this is the same decision restated at data level: events exist
to be read, not to be replayed into state.

The test of this rule: **if the events table were deleted, the product would still work** — you would
lose the timeline and the analytics, not the product. If deleting a table breaks the core, it is
carrying authoritative state, and that is the line we are drawing.
